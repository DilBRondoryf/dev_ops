Итоговая защита

Выполненная цепочка

lab/app.py + lab/Dockerfile
        -> python unittest в контейнере
        -> devops-student:local
        -> api/web в compose.student.yaml
        -> Prometheus targets и HTTP metrics
        -> Grafana dashboard
        -> stop api / 503 / up=0
        -> start api / up=1 / сохранение данных


Воспроизводимый запуск:

docker compose -f compose.student.yaml build api web tools ansible
docker compose -f compose.student.yaml up -d
docker compose -f compose.student.yaml --profile monitoring up -d
docker compose -f compose.student.yaml ps


Отчёты: [K4-01](K4-01.md), [K4-02](K4-02.md), [K4-03](K4-03.md), [K4-04](K4-04.md). CI workflow: [Student CI](../.github/workflows/student-ci.yml), предыдущий разбор запуска и ссылок на Actions сохранён в [K3-05](K3-05.md). Базовый SHA до изменений KT4: `1fc0b22`; локальный образ собран из `lab/Dockerfile` и имеет label `course.student=dames`.

Сеть Compose соединяет web с api по имени сервиса `api:8000`; наружу опубликован только web на `localhost:8080`. Заявки и banner лежат в общем Docker volume `requests`, поэтому перезапуск процесса не удаляет SQLite и файл banner. Prometheus ходит к `/metrics` по внутренним именам `api` и `web`, Grafana использует datasource `Workshop Prometheus`.

Индивидуальное изменение: после первоначальной проверки banner сообщение изменено на `DevOps workshop student: dames | KT4 monitoring ready`; повторное применение Ansible дало `changed=1`, новый текст виден через `/api/banner`.

Перед настоящим выпуском нужна проверка на чистом окружении с нуля: собрать образ из конкретного commit SHA, прогнать тесты и healthcheck, проверить восстановление из резервной копии данных, а также отдельно проверить секреты, права и нагрузочное поведение.

Ответ на вопрос: следующая проверка перед выпуском — воспроизводимый smoke/e2e-прогон в чистом окружении с проверкой восстановления данных и наблюдаемости, а не только успешная локальная сборка.
