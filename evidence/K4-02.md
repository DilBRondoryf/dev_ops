Prometheus и Grafana

Запуск мониторинга

docker compose -f compose.student.yaml --profile monitoring up -d
curl.exe -s http://localhost:9090/api/v1/targets
curl.exe -s "http://localhost:9090/api/v1/query?query=up%7Bjob%3D%22workshop%22%7D"


Prometheus показал две цели со статусом `up`: `http://api:8000/metrics` и `http://web:8000/metrics`. Запрос `up{job="workshop"}` вернул `1` для `api:8000` и `web:8000`, то есть сами targets доступны.

После нескольких запросов к списку заявок:

devops_http_requests_total{role="web",status="200"} = 4
rate(devops_http_requests_total{role="web",status="200"}[1m]) = 0.05477


Счётчик показывает накопленное число успешных ответов web с момента старта процесса. `rate` показывает среднюю скорость прироста счётчика за последнюю минуту; в панели единица задана как `requests/sec` (`reqps`).
Dashboard `Workshop HTTP Requests` создан с datasource `Workshop Prometheus`, uid `workshop-prometheus`, и двумя панелями: counter и rate. Экспорт: [K4-02-dashboard.json](K4-02-dashboard.json).
Счётчик может сброситься после перезапуска контейнера, потому что `COUNTS` хранится в памяти процесса. Это не удаляет заявки: они сохраняются в SQLite на Docker-томе `requests`. Prometheus и запрос `rate` должны учитывать такой reset при расчёте временного ряда.

Вывод: обе цели доступны, метрики читаются, панель отображает абсолютное значение и скорость изменения после нагрузки.
